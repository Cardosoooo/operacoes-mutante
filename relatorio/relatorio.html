1. Introdução

Este relatório avalia, com teste de mutação, a suíte de testes do projeto operacoes-mutante: uma biblioteca de 50 funções matemáticas em JavaScript, testada com Jest. A ideia foi descobrir se a suíte realmente pega erros no código, entender por que os mutantes sobreviveram e escrever testes para matá-los.

Repositório: https://github.com/Cardosoooo/operacoes-mutante

Configuração: instalei @stryker-mutator/core e @stryker-mutator/jest-runner (versão 10.0) e rodei npx stryker init. No assistente, não usei preset, escolhi o Jest, mantive os reporters padrão (html, clear-text e progress), o npm e o formato JSON. Nesta versão o arquivo gerado se chama stryker.config.json; o stryker.conf.json do enunciado ainda é aceito, mas deixou de ser o nome padrão. A configuração usa coverageAnalysis: "perTest", então cada mutante é testado só pelos testes que passam pelo trecho alterado. Também criei o script npm run mutate para rodar a análise.

2. Análise Inicial

Os 50 testes originais passam, e a cobertura do Jest (npm test -- --coverage) é alta: 98,64% das linhas e 100% das funções, com 85,41% de statements e 58,82% de branches. A primeira execução do Stryker, porém, deu um mutation score de 73,71% (Figura 1).

Essa diferença acontece porque a cobertura só mostra se uma linha foi executada. Ela não diz se algum teste conferiu o resultado daquela linha. Todos os 44 sobreviventes estão em linhas cobertas: os testes passaram por elas, mas nenhum percebeu a alteração. Os números de statements e branches já davam uma pista. Cada função era chamada uma vez, quase sempre pelo caminho feliz, sem chegar aos throw e sem testar o lado falso das condições. Olhando os 56 mutantes não detectados um por um, separei as causas na Tabela 1.

3. Análise de Mutantes Críticos

3.1 Conversão de temperatura: celsius * 9/5 virou celsius * 9 * 5

O teste 38 converte 0 °C e espera 32 °F. Como o zero anula a multiplicação, 0 * 9/5, 0 * 9 * 5 e 0 / 9 / 5 dão todos 0, e o resultado continua 32. A linha está coberta, mas o valor escolhido torna o fator irrelevante: qualquer fórmula do tipo celsius * k + 32 passaria. O teste 39 tem o mesmo problema: ele converte 32 °F, e como 32 - 32 dá 0, os dois mutantes de fahrenheitParaCelsius também sobrevivem.

3.2 Mediana: a ordenação foi removida

O Stryker trocou [...numeros].sort((a, b) => a - b) por [...numeros]. O único teste da mediana usa [1, 2, 3, 4, 5], que já está em ordem: ordenar ou não dá o mesmo array, e o elemento do meio continua 3. Por isso também sobreviveram as trocas do comparador por () => undefined e por a + b. Além disso, o array tem tamanho ímpar, então o ramo do array par nunca rodou: a linha 112 é a única descoberta no relatório de cobertura, e os 4 mutantes desse ramo ficaram sem cobertura. Ou seja, o teste usava justamente uma entrada em que a ordenação não faz diferença.

3.3 Clamp: valor < min virou valor <= min

O teste 36 chama clamp(5, 0, 10), um valor dentro do intervalo. As duas condições são avaliadas, por isso a linha aparece coberta, mas os return min e return max nunca rodam; trocar qualquer um dos if por false não muda nada. O mutante da figura é o mais sutil: nem o teste de fronteira que o exemplo do enunciado recomenda, com o valor igual ao limite (clamp(0, 0, 10)), o mata, porque quando valor === min tanto faz devolver min ou valor, o número é o mesmo. A única entrada que separa as duas versões é o zero com sinal. No original, clamp(-0, 0, 10) devolve o próprio -0, pois -0 < 0 é falso; no mutante, -0 <= 0 é verdadeiro e a função devolve o limite 0. Como o toBe do Jest compara usando Object.is, que diferencia 0 de -0, dá para testar isso.

4. Solução Implementada

Mantive os 50 testes originais e adicionei 27 em um novo bloco, “Testes que matam os mutantes sobreviventes”, agrupados por função (test/operacoes.test.js, linhas 78 a 215). Cada teste foi escrito para falhar com um mutante específico, e todos passam no código original (npm test: 77 aprovados). A Tabela 2 mostra os que matam os mutantes da seção 3.

Os outros testes seguem a mesma ideia e se dividem em três grupos. O caso falso das funções booleanas, incluindo a igualdade, que separa > de >=: isMaiorQue(5, 5), isMenorQue(5, 5), isPar(7), isImpar(4), isDivisivel(10, 3) e isEqual(7, 8); no isPrimo, os compostos 4 e 9 obrigam o laço a achar um divisor, e o 1 separa n <= 1 de n < 1. As validações: a entrada inválida com toThrow e a mensagem esperada, o que também mata a troca da mensagem por texto vazio, e o valor válido na fronteira, como raizQuadrada(0) e fatorial(0), que mata a troca de n < 0 por n <= 0. Os casos vazios, como mediaArray([]) → 0: sem o if, a função faria 0 / 0 e devolveria NaN.

Considero esses testes eficazes porque cada um foi escrito pensando em um mutante específico e conferido rodando o Stryker de novo. Eles também verificam só o resultado da função (o valor ou o erro lançado), sem depender de como ela foi implementada. Durante a análise, percebi ainda que as mensagens de maximoArray, minimoArray e medianaArray têm “не” (em cirílico) no lugar de “não”. Como o foco do trabalho são os testes, não mexi no código: os testes conferem só o final da mensagem, e deixo o problema registrado aqui.

Com os novos testes, 208 dos 213 mutantes passaram a ser detectados. Os 5 que sobraram são equivalentes: eles alteram o código, mas a função continua devolvendo os mesmos resultados, então nenhum teste consegue matá-los.

  • fatorial, linha 19 do código original (4 mutantes): o if (n === 0 || n === 1) return 1 trocado por false, por && ou com um dos lados falso. Para 0 e 1, o laço for (let i = 2; i <= n; i++) não executa e a função devolve resultado = 1, o mesmo valor do retorno antecipado.
  • produtoArray, linha 84 (1 mutante): sem o if, o reduce com valor inicial 1 também devolve 1 para o array vazio.

Para esses casos, usei o comentário // Stryker disable next-line <mutador>: motivo, que é a forma que o próprio Stryker oferece para marcar mutantes equivalentes. Eles passam a aparecer como Ignored e não entram no cálculo; o código continua funcionando igual. O comentário vale para todos os mutantes daquele tipo na linha, então acabou ignorando também 2 que já estavam mortos (as trocas da condição por true). Por isso aparecem 7 ignorados. Os 3 timeouts são laços infinitos (i++ virando i-- no fatorial e duas mutações no while do mdc), e o Stryker conta esses casos como detectados.

No final, o score ficou em 100% (206 de 206, Figura 5). Sem os comentários ele seria 97,65%, e os 5 mutantes que faltam são justamente os equivalentes. A cobertura também chegou a 100% nas quatro métricas. Esses mutantes mostram ainda que os dois if são redundantes e poderiam ser apagados, mas não mexi neles porque o trabalho é sobre a suíte de testes.

6. Conclusão

Antes deste trabalho, eu olharia para 98,64% de cobertura e acharia que a suíte estava boa. O teste de mutação mostrou que não estava: os testes passavam pelo código, mas muitos não conferiam quase nada. Eles testavam um caso só por função, usavam valores como 0 °C, que escondem erros na fórmula, e testavam a mediana com um array que já estava ordenado. O que achei mais útil é que cada mutante sobrevivente mostra exatamente qual teste está faltando. Por outro lado, a ferramenta não resolve tudo sozinha: precisei analisar caso a caso para saber quais mutantes eram equivalentes, e no clamp um que parecia equivalente não era. Mesmo assim, para saber se os testes pegariam um erro de verdade no código, o teste de mutação diz muito mais do que a cobertura.
